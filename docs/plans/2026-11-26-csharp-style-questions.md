# C# style questions for migration step 6

The owner recorded decisions on 2026-11-26 and 2026-11-27 and confirmed items 4–9 for the rollout. [Migration plan, step 6](2026-11-15-godot-migration.md#step-6-tidy-the-c-codebase-owner-2026-11-20-after-step-5-on-net100).

## Owner decisions

### 2026-11-26

1. Use `var` when the initializer shows the type.
2. Brace every control body, including single-line guards.
3. Put `using` directives at file scope.
4. Use `_camelCase` for instance fields, `s_camelCase` for mutable statics, and PascalCase for constants and static readonly fields.
5. Require `when_types_exactly_match` for collection expressions. Review every IL difference because lowering can change construction or capacity.

Land each rule in six commits, one per area. Simulation covers DK2.Simulation, DK2.AI, DK2.Pathfinding and DK2.Core. Data covers DK2.Data, DK2.Data.Model, DK2.Assets, DK2.Art and DK2.Convert. Presentation, Tools and Harness together, the Godot adapter, and tests are the other four areas. Enable each rule in scoped `.editorconfig` sections as its area lands. The final commit for the rule moves it to `[*.cs]` and removes its scoped sections.

For pure-format rules (`var`, braces, field naming and collection expressions), compare the Release assemblies of every changed project before and after. Use `ildasm` or metadata to compare IL, ignoring only MVID, PDB identity and timestamp differences. Build, run `dotnet format --verify-no-changes`, and run the test suite for every area commit. If IL differs, list each changed method and explain the difference or revert it. Run the turn-400 hashes for Level1, Level6a and Level7 for any commit with an IL difference, plus frame captures if the difference is in presentation or Godot code. Run the same hash triple after each rule's final commit.

The approved brace policy uses `csharp_prefer_braces = true` (IDE0011), with 1,589 files in the sampled pool before analyzer exclusions.

### 2026-11-27

1. Use block bodies for methods, constructors, operators, conversion operators, properties, indexers, accessors and local functions. Set the corresponding `csharp_style_expression_bodied_*` options to `false` at warning severity and use the built-in fixes (IDE0021–IDE0027 and IDE0061). Keep lambda style unchanged, so the lambda option and IDE0053 are outside the rollout.
2. Write the type on every object creation. IDE0090 offers conversion toward implicit object creation, so add a Roslyn source guard against `ImplicitObjectCreationExpressionSyntax`. Use the semantic model's converted type to write the explicit type, including generic arguments and `global::` qualification where needed. For nullable value-type targets, construct the underlying type to preserve the original value. Keep the approved collection-expression policy.
3. Replace the 228 class and struct primary constructors with explicit constructors. Store captured parameters in private readonly `_camelCase` fields. Use a mutable field where the type writes the parameter and list each case. Preserve initialization order and the values read by initializers. Add an architecture-test guard and retain positional record syntax.

4. Enforce file-scoped namespaces (IDE0161) and System-first import order.
5. Use camelCase for locals and local constants. Leave async names to review. All 27 surveyed async methods omit the suffix.
6. Leave pattern matching to review. The survey found 117 `== null` and `!= null` comparisons combined that bind to user-defined operators.
7. Use `readonly` and `sealed` as review guidance. Enforce removal of optional `this.` qualification (IDE0003) and prefer default literals (IDE0034).
8. Keep member order and the number of types per file flexible.
9. Use a shrinking baseline to enforce named enum members for numeric casts. Handle raw DK2 IDs and same-type primitive parameter runs case by case in phase D.

### Rollout order

Start with the mechanical rules in items 4, 5 and 7, followed by block bodies, explicit object creation and explicit constructors. Land each rule in six area commits with the Release builds, IL comparison, formatter verification and test suite specified above. Expect identical method IL for block bodies and explicit object creation. For every explicit-constructor area, run the full turn-400 hash triple and frame comparisons, and report the field and constructor IL changes. Verify the enum-cast checks before starting phase C.
