# Temple sacrifice recipes

**Scope:** DKII.EXE v1.70 and the shipped `GlobalVariables.kwd` sacrifice
table. Binary conclusions are **STRONGLY INFERRED**; no claim here is
CONFIRMED without an original-game observation.

## Result

The Temple keeps the last three offerings made to each room and compares the
newest suffix against 44 ordered recipes. A match clears the remembered
sequence and creates a creature, crate, or special at the offering point. A
miss removes a creature or object offering but leaves the rolling history
intact; any keeper-spell cost occurs outside the handler read here.

The executable does not use balance variable 112 in this mechanic. Its reader
belongs to Temple prayer and increases the mana generated by a converted
creature. The inherited name `PercentageOfManaGainedBySacrificing` is wrong.

## Storage

The shipped file record is 12 bytes:

| bytes | meaning |
|---|---|
| 0..5 | three `(u8 type, u8 id)` ingredient slots |
| 6 | reward type |
| 7 | notification/speech variant |
| 8..11 | signed 32-bit reward value |

DKII.EXE expands each record to 34 bytes. Its world holds a 128-entry table at
world offset `+0x2E70`, with the loaded count at `+0x731B`. Initialisation
clears all 128 entries, loading refuses a 129th, and the world checksum includes
the full reserved table. **STRONGLY INFERRED.**

The runtime record is:

| offset | meaning |
|---|---|
| `+0x00`, `+0x06`, `+0x0C` | three six-byte ingredient entries |
| `+0x12` | ingredient count |
| `+0x16` | reward type |
| `+0x1A` | reward value |
| `+0x1E` | notification/speech variant |

Each ingredient entry holds a 32-bit type, an 8-bit id, and an 8-bit creature
level. The file has no level byte; it is supplied when a live creature enters
the pool.

## Intake and room history

The Temple is room type 13. Three binary paths add offerings:

| type | offering path | recorded value |
|---|---|---|
| 1 | creature Temple/prayer state at `0x00472930` | creature type id and current level |
| 2 | non-gold object state at `0x0049F600` | object type id, level zero |
| 3 | game action `0x87`, handler `0x005133A0` | keeper-spell id, level zero |

The type names are **STRONGLY INFERRED** from the binary paths and corroborated
by OpenKeeper's independently decoded enum. Gold objects take a separate branch:
they do not enter recipe history and emit notification variant 7.

History is per Temple room, not per keeper. It is a three-entry circular buffer
at room `+0x49`; `+0x5B` identifies the newest slot, `+0x5C` the next insertion
slot, and `+0x5D` is a count clamped to three. Function `0x004F1600` appends an
offering. **STRONGLY INFERRED.**

## Matching

Function `0x004F1660` scans recipes in file order and stops at the first match.
For each recipe it compares the newest offering with the recipe's last
ingredient, then walks backwards. Consequences:

- ingredient order is exact and chronological, not a set;
- a two-item recipe matches the newest two entries even when a third, older
  unmatched entry remains in the buffer;
- type and id must both match;
- the first matching record wins if authored recipes overlap.

A successful match clears that room's entire three-item history before its
reward is executed. A miss retains the history, allowing the next offering to
complete a recipe. **STRONGLY INFERRED.**

## Rewards

Function `0x004F1780` dispatches the reward at the location of the newest
offering:

| type | binary behaviour | shipped recipes |
|---|---|---:|
| 1 | create the creature named by the low byte of `rewardValue` | 21 |
| 2 | create a neutral object named by the low byte of `rewardValue` | 23 |
| 3 | gold-producing location path | 0 |
| 4 | add mana to the player and update its statistic | 0 |

The names gold and mana are **STRONGLY INFERRED** from their binary effects and
corroborated by OpenKeeper's enum. Their exact amount/placement rules remain
UNKNOWN because no shipped recipe reaches them.

For a creature reward, the matcher averages the recorded levels of type-1
ingredients using integer division and adds that level in the high word of the
reward value. The spawned creature is promoted to that level. Keeper-spell and
object ingredients do not participate in the average. **STRONGLY INFERRED.**

On a match, event family `0x47` receives the recipe's speech variant when it is
non-zero. A miss uses variant 1. The exact spoken lines remain UNKNOWN.

## Variable 112 is prayer mana

The sole reader of cached variable 112 is in the Temple prayer hook beginning
at `0x0047B970`, not in any sacrifice intake, matcher, or reward routine. The
hook first applies variable 115's health change while praying, then derives
prayer mana from the creature definition and level. For creatures carrying
instance flag `+0x3EA` bit 4 it applies:

`mana += mana * (variable112 + 100) / 100`

and credits the result to the owning player. With the shipped value zero, the
flagged creature produces exactly twice its ordinary prayer mana. The manual
independently says converted enemies generate twice as much mana while praying,
which identifies the flag and purpose. **STRONGLY INFERRED.**

Therefore `PercentageOfManaGainedBySacrificing` is a misleading inherited
identifier. It should be read as the converted-creature prayer-mana bonus until
the model is renamed. The shipped sacrifice table itself has no mana reward.
