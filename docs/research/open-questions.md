# Open research questions

Living list. Every entry needs an experiment or RE dig before implementation
may treat it as fact.

**Many of these can be answered by playing the game.**
`observation-checklist.md` collects the ones a person in front of DK2 can settle
by looking, as concrete experiments, and says which ones playing cannot settle.
Check it before writing anything up as UNKNOWN.

Conventions. Rows are never renumbered, reordered or deleted, so file order is
not numeric order — see "Numbering" at the end. The Status cell opens with the
state (OPEN, UNKNOWN, HYPOTHESIS, ANSWERED (source, date), BUILT (ADR-nnnn),
WITHDRAWN, SUPERSEDED, CUT) and carries the answer, its confidence tag and a
pointer to the note, ADR or test that holds the evidence. The Blocking cell says
what the question stops, and names a live divergence from DK2 where one is
known. A shipped variable recorded as CUT has no reader in `DKII.EXE`; one
recorded as DISABLED has a reader and ships as zero (ADR-0085).

Allocating a number: take the one after the highest in this file. **Q121 is a
hole** — never allocated, never to be reused. **Q39 labels two rows**, both
kept; Q37a, Q37b, Q55x and Q118c are separate suffixed ids rather than
duplicates, and none of the four is a mistake to fix.

## The Hero Portal — Q86's last amendment, and four questions numbered after Q234

**Q86 closed further, not reopened** (owner, 2026-09-07): *"hero portal IS AN ENTRANCE,
but for goodly heroes (rival faction)"*, and *"a keeper claims a hero portal room… it just
becomes an indestructable dead room that can't be sold or repurposed."* Both CONFIRMED, and
both were partly divergent here. See `portals.md`, "The Hero Portal is an entrance too".

Portal (3) and Hero Portal (25) have **byte-identical** room flags, terrain flags and
41-byte handler records, so DK2 runs **one** implementation for both. What separates them
is a single condition in the candidate builder — `def+0x686 & 0x400` when the room is
type 3, `def+0x68a & 8` when it is type `0x19` — so the two rosters are **exclusive by room
type, not by owner**. The dead-room properties need no new rule: no `Buildable` flag means
`CanSell` refuses it and nothing can be built over it (Q207), and the absence of the
room-level `Attackable` flag is the "indestructible".

Two divergences found and fixed. (a) `CanComeFromPortal` took no room, so a keeper's
claimed Hero Portal produced the keeper's *evil* creatures — the doc comment on that method
had predicted the bug and dismissed it as costing nothing. (b) Capacity counted only
portals that could produce; DK2's counter tests the room type and nothing else, so a broken
portal and a dead claimed Hero Portal both still raise the cap (Q98).

**Player-facing name:** the game calls an unclaimed one a **"Mercenary Portal"** (Q211).
There is no "Hero Portal" string in the game at all — that is the editor's label in
`Rooms.kwd` 25, which is where `RoomTypeId.HeroPortal` and
`CreatureFlags2.AvailableViaHeroPortal` take their names. Identifiers stay; presentation
text should say Mercenary Portal.
