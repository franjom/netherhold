It walks the 46 types; a type qualifies only if it is not unique and carries the portal flag with room type 3 or the hero flag with room type 25, so the room type, not the owner, picks the side (portals-mercenary.md §2). The weight comes from the type's first attraction: a Lair gives 1.0 (3.0 for the Goblin's lair object 0x16), any other room sums 0x004DCE70's per-room contribution less 1.0 per creature of the type held; then the CreatureEntranceInfo boost and sack block (player+0xB57) scale it, and one random draw over the running total picks the type. It creates the creature through 0x004DC9A0, increments room+0x4D (at 0x004DC5E3) and decays every non-zero boost and block by 1.0; the noticing pass 0x004DBD90 runs first. portal-creature-action.md marks the selector's use of the first attraction CONFIRMED and the draw STRONGLY INFERRED, matched by the Level 2 recording's arrival order; built under ADR-0272. binary-entrance.md §4.1 describes the same builder as "0x004DC0F0-ish" and AttractionBudget.cs cites 0x004DC0F0; that address falls inside this function, and §4's HYPOTHESIS heading predates the resolved reading. Re-read whole 2026-10-01 for Q505. The increment at 0x004DC5E3 is conditional on 0x004DC9A0 returning non-zero. The decay loops run whenever any type was weighted (the entry count is non-zero) and the argument is 1, whether or not the create succeeded. So a roll refused by the creator, for example with PortalsOpen clear, still consumes the draw and decays the boosts, and the caller 0x004DBBE0 restamps the clock regardless. Within the type loop, a keeper at its capacity (portal-made creatures, body +0x3E6 bit 1, against the low byte of 0x006F28B4 plus the high byte per further portal) skips the type and, with argument 1, posts message 0x0F (fewer than two portals) or 0x10. In seed 04 the Warlock row's boost reads 8.0, 6.0 and 4.0 after the rolls at 967, 1051 and 1147, which is 2.0 per roll against the 1.0 read here (Q507).
