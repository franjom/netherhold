The key handler runs the post-result arm only while the player's `Status` is non-zero (test at `0x004054F0`). In the Won single-player branch Escape (scancode `0x01`) sets player `+0x109E` and bit `0x100000` of `+0x76`, then issues action 75; Space (`0x39`) issues action 1 in every branch; in other game modes Escape issues 134 and then 75 at once. Read from the binary in game-actions.md §3.1 and not checked against a capture, so HYPOTHESIS; only this arm of the handler is described. `CampaignResultFlow.UpdateWinKeys` mirrors the won-result arm's keys (Escape: action 134 then 75 once the win screen is done or absent, 75 alone while it runs; Space leaves the level without posting action 1, see 0x00510F40); the arm of the other game modes (My Pet Dungeon) is not mirrored, and ours posts nothing on Escape after a loss.

The skip (read 2026-10-17, camera-paths.md §5): a key press of Escape (while 0x0075A661 is 0) or Space (unless player +0x76 bit 0x400000 sends it to another action) reaches 0x00405362. In camera mode 0x12 it calls SpeechSystem_Clear(0x28) and Camera_EndPath 0x0044D8F0. With a move in flight (+0xDFA) or a yaw turn (+0xE20) it clears the speech queue with 0 and finishes that move in 1 ms (0x0044A270(1), 0x0044A550(1)). Otherwise the key falls through to the bindings. SkipCameraPathCommand mirrors the path branch (ADR-0496).
