Reached through the creature cleanup slot +0x30 (0x0048AF80) once health is below 1. It increments the killer keeper's per-victim-owner tally at player+0x19E indexed by the victim owner's Number, and, unless creature+0x3E6 bit 0x40 is set, the victim owner's creatures-lost dword at player+0x173 (player-object.md; condition type 22 reads both, Q276). Inside it the gold spill at 0x0048814B, the carried object and dragged creature releases, and the owner-list unlink at 0x00488468 are recorded (imp-mana-removal.md, creature-ownership.md), and the corpse gate tests definition bit 0x8000 with runtime bit 0x20. Credit and hero count (0x0048822F..0x0048832A, read 2026-10-23): only when health is at or below 0 (+0x40 <= 0). The credited player is the tag in the victim's word +0x36 (the source the health routine 0x004B2CE0 stamps on every health change); when that is 0, the owner word +0x28 of the first non-zero attacker scanning i = 0..7, spell +0x504[i] before melee +0x514[i]. With a credited player and the victim's +0x3E6 bit 0x40 set, nothing is counted at all (the tally, the hero count and +0x173 are all skipped, 0x004882A9). Otherwise, when the victim's definition +0x686 has bit 8 (IsGood), the credited player's dword +0x14A (HeroesDestroyed) is incremented, and in game mode 4 (0x0075AD4B) with the credited player's Number at least 3 world slot +0x344 adds MpdScoreHeroKilled (0x006F29D5); when not IsGood and the credited tag differs from the victim's owner word +0x28, +0x146 (EnemyCreaturesKilled) is incremented instead. No owner test guards the hero count. It also fires the Killed trigger event (trigger-walkers.md). The portal tally (2026-10-04, Q508): at 0x00488150-0x00488170 it reads the creature's word +0x4EB, the portal room's tag that Portal_CreateArrival stamps. When that is non-zero and the thing's dword +0x4D is above 0, it decrements the dword (load, JBE past at 0, DEC, store), so the tally never goes below 0. Nothing checks that the thing is still a portal. EBP is 0 on both paths in (0x0048808F, 0x0048813E). Read instruction by instruction. Built as `PortalRules.ArrivalDied` with `CreatureState.PortalEntranceTile` (ADR-0358). The counter write is read instruction by instruction; the other effects are marked strongly inferred, so HYPOTHESIS. Built as CreatureHealthSystem.Die with CreatureDeathRules.LeavesBody (ADR-0277).

The killed event (disassembly and decompile re-read 2026-11-11, STRONGLY INFERRED). The function's only creature-event call, `0x0049AA30(creature, 4, 0, 0)` (killed), is at 0x00487CF5. Before it, 0x00487CCB/0x00487CCD tests `+0x3E6` bit 0x40 and jumps to 0x00487DD2, past the event. The same bit also skips the +0x173 count, the death sound, the carried-gold drop (`Creature_DropCarriedGold` runs only with the bit clear, so no gold spill) and turns the carried-thing and dragged-thing drops into a plain removal, so an uncounted creature fires no killed event, counts nowhere and spills nothing. The event is also skipped when world `+0x7239` bit 0x40 is set or the owner player's `+0x76` bit 0x2000 is set (0x00487CD9, 0x00487CE5). Our DeathUncounted mirrors the bit but nothing sets it, which is why creature action 35's byte 0 (0x0049AC80 sets 0x40) is a gap (openkeeper-pr-audit-1000-1110.md item 4).

The mixed-slot adapter boundary remains: `CreatureHealthSystem.CreditHeroKill` chooses `EngagedMelee[i]` before `EngagedRanged[i]`, while the native raw-offset order above means spell before melee. `HeroesDestroyedTests` pins the current adapter order; neither it nor this task establishes parity for that tie. No credit behavior changed in ADR-0610.
