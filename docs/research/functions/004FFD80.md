Read whole 2026-10-28 by decompiler. thiscall on the computer player; arguments allowance (byte), x, y; returns the allowance, less one when a blueprint was laid. Every draw is Random_Next on the world stream +0x15A0.

Door, when Random_Next(4) < (+0x4B2 >> 12) & 7 (TrapVsDoorPreference): for id = 1 .. world slot +0x13C (door count), the definition from slot +0x138(id) is skipped when its byte +0x8B has 0x40, and 0x004BACD0(id) must return 3 (the player's availability table, sorted 9-byte entries at +0x62, count +0x5E, value at +1, 1 when absent). An eligible id is remembered, then stop = (+0x4B2 & 0x18000): 0 -> 0, 0x8000 -> 2, 0x10000 -> 1, 0x18000 -> 0, and the loop ends on Random_Next(100) <= stop * 50. So DoorPreference 1 stops at the first eligible door, 2 at each with probability 51/100, and 0 or 3 at each with probability 1/100; with no stop the last eligible door is laid. No eligible door returns the allowance unchanged; so does a failing world slot +0x244 test (the door placement test 0x00450DB0) at (x, y); otherwise 0x004C33B0(x, y, id) lays it and the allowance less one is returned, whether or not the keeper could pay.

Trap otherwise: boulder = 2 when 0x004BAE30(2) is 3, else 0. For id = 1 .. slot +0x164 with 0x004BAE30(id) == 3: the boulder, when +0x4B2 bit 29 (BoulderTrapsOnLongCorridors) is clear, is remembered and stops on (+0x4B2 >> 9) & 7 < Random_Next(4); with bit 29 set it is taken and stops only if some direction of the table 0x006BC350 (N, E, S, W) has its next four tiles pass 0x004FFA50, and is otherwise not remembered. Another trap is remembered and stops on preference < Random_Next(5) when its definition (slot +0x160) has byte +0xBD == 1, else on Random_Next(5) < preference. The laying is the same through slot +0x24C and 0x004C3860.
