Read 2026-11-13 (decompile and disassembly). Method on the sound device (vtable 0x00674208, thiscall), arguments (result slot, key, block, voice handle or -1). With handle -1 it resolves the voice from the key through 0x00618D30 (-1 fails); then, for the block's `+0xC` bits 0x1A it calls backend slot +0x78. It reads the block's mask at `+0x14` and applies in this order: bit 0x2 (block +0x30 into the voice record +0x64, slot +0x8C); bit 0x400000 (block +0x70 as a percentage of that value, slot +0x8C); bit 0x80000 (block +0x60, slot +0x48, skipped when it equals the constant at 0x00674230); bit 0x100000 (block +0x64, slot +0x54); bit 0x20 (block +0x2C, slot +0x9C); bit 0x40 (0x00618C50); **bit 0x200 (backend slot +0x70 with the result slot, the voice handle and the address block +0x3C: the three floats of SoundInstance_BindVoice 0x0060CDB0, minimum, maximum, third)**; bit 0x1 with block +0x34 non-null (slot +0x84, the source position pointer, so the mapping is set before the position); bit 0x100 (block +0x38, slot +0x88). What the slots other than +0x70 do was not established. Callers: the device slots +0x14 (0x00617390, which requires device +0x24 bit 0 and a block) and +0x18 (0x006173D0), and 0x00617090 (which passes a zeroed block with mask 0x1000, so no distance mapping). The backend object it calls is device +0x18, created by 0x00618040.

Only SoundInstance_BindVoice sets mask bit 0x200 in the sound code, so every spatial voice the binder accepts reaches slot +0x70 here, and a head-relative one never does.
