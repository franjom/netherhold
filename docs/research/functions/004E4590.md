Called from Room_OnTilesChanged (0x004E449E). By type byte +0x18: 3 and 0x19 (Portal, Hero Portal) set CentrePos to the first slab (+0x2D/+0x2E) plus one on each axis; 5 (Heart) sets it to the first slab plus three and the floor-slot position to plus one; 0x12 to 0x18 set both to the first slab. Any other type walks the chain (tile word +4 of the runtime map is the next slab), sums the coordinates, divides by the count, and takes the centroid when world slot +0x1FC says it is in bounds and the tile's room tag (+2 low twelve bits) is this room's; else a square spiral from the centroid (steps 1, 1, 2, 2, ... turning through the four directions) takes the first such tile. The floor-slot position takes the first such tile that Room_IsFloorSlot rejects. Type 9 (Guard Room) first records its bounding box at +0x49..+0x4F. The keeper's attack planner, front and room choices read CentrePos as a room's position; KeeperView.PositionOf mirrors the rule with the room tile nearest the centroid in place of the spiral.

The dispatch, read 2026-10-04: types above 0x19 skip it (0x004E45B4). The type indexes the bytes at 0x004E4AD8 (type 3 -> 1, 5 -> 2, 0x12..0x18 -> 3, 0x19 -> 4, others 5 or 0), which index the jump table at 0x004E4AC0 (0x004E460C, 0x004E45E9, 0x004E45D0, 0x004E45F9, 0x004E45E9, 0x004E460C). The Heart arm at 0x004E45D0 stores FirstSlab + 3 into +0x27/+0x29 (LEA from the first slab's x and y). That is why a 5x5 heart's CentrePos sits one tile past its centre in captures (Q515). That a placed heart's FirstSlab, the chain head, is its low corner is inferred from those captures.
