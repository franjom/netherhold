When `player+0xB53` is set and due it sends message 0x2E, then walks the player's creature chain: a payable, non-exempt creature with `GetPaid` (`+0x3E2`) clear accrues its wage (`0x0048B6B0`), has its failed attempts `+0x474` zeroed and tries to collect (`0x00472320`); one with `GetPaid` set only has it consumed, so a treat prepays exactly one payday. It then sets `+0xB53` to now plus `PayDayFrequencySeconds` (global `0x006F25D1`, which it is the reader of) times ticks per second, and `+0xB4F` to now. Read from the binary; no capture pins the timing, so HYPOTHESIS. PaydaySystem mirrors it.

Order of the announcements (disassembly re-read 2026-11-11, STRONGLY INFERRED). `Message_Post(0x2E, player, 0, 0, allocate 1)` is at 0x004BE1E3, before the wage loop; after the loop ends, `Trigger_FirePlayerEvent` 0x004C7A50 is called as (this player, 0x2E, 0, 0) at 0x004BE250, which is player event 46 (LEVEL_PAY_DAY) for the paid player, and only then do the `+0xB53` reschedule and the `+0xB4F` stamp follow. So the event fires after every creature has been handled and before the next payday is scheduled. Ours has no producer for event 46 (openkeeper-pr-audit-1000-1110.md, PR 1032: one shipped record, the level 1 tutorial pay-day speech, which never plays now).

Called by World_UpdateTurn 0x0050A450 at 0x0050A7BE, once per player except the two special players, before the entity sweep 0x004B7830, so a creature sent to state 187 here runs that state's handler in its own update the same turn.
