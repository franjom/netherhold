Thiscall on the creature with one argument, the keeper's player id; both its callers are in Hand_HandleSecondary 0x00408EE0 (0x00409229 for an own creature, 0x004092B2 after the pick-up permission 0x0048E6A0 for another keeper's). It returns 0 when any of these holds, else 1:
- the definition's +0x686 bit 2 (CanBeSlapped in our flag enum) is clear;
- the creature's +0x3E6 bit 21 is set (dying);
- the word +0x3CB (the keeper whose prison holds it) is non-zero and not the argument;
- the current state +0x25E is 0x4C (76, the hand's drop, still falling);
- the definition's +0x686 bit 14 (IsHorny) is set and the creature's +0x46F bit 0 is clear.
So a keeper cannot start a slap on a creature that was just dropped and has not landed; the swing, the slap action and every slap effect are skipped. Ours reaches the same outcome later for a non-Horny: HandRules.CanSlap has no state test, but HandSystem.OutcomeOf returns Nothing for LandingPending or states 76, 101 and 193 (HandSystem.cs, the slap arm tests), and HandRules.HasPickupPermission refuses 76 and 193 for the cursor's other arm. A Horny is modelled (ADR-0776): CanSlap admits one while ReaperCanAcquireFight (+0x46F bit 0) is set and its state is not 76, and the slap then dismisses it (Hand_SlapCreature 0x0048B8A0, Horny branch). Bit 0 is set by Creature_Construct (byte 9), the state-237 tail 0x004748A0 and state 238; cleared by Shot_CreateReaper, the countdown end, the slap branch, the finale (0x004BF804, 0x004BF85A) and the mana depart 0x00491B70. The computer keeper's slap step 0x00502F00 does not call this predicate: its action reaches 0x0048B8A0 through 0x00513690 and 0x004C0F80 with no gate, so an AI keeper can dismiss its own Reaper in any state, even arriving or greeting (a suspected original defect, ADR-0776). Ours' KeeperAI.Slap filters on CanSlap and so cannot.
