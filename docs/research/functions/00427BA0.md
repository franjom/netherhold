Full decompile read 2026-10-17. Fastcall on a HUD object: `this+0x53` is a player-like object whose virtuals answer each test, `this+8` a word passed to its `+0x260`.

- Widget objects come from `FUN_0052C540(id)`; `+0x48` is a visible flag, `+0x14/+0x18/+0x1C/+0x20` a rectangle (x, y, then two kept fields, read as width and height).
- Six widgets, in order, each shown when its test passes:
  - `0x2D`: player virtual `+0x34C` non-zero;
  - `0x2E`: `+0x348` non-zero;
  - `0x2F`: `+0x364` (short) non-zero;
  - `0x30`: global byte `0x006F2957` bit 5 set;
  - `0x31`: `+0x36C` minus a field `+0xEE6` of the `+0x260` object is not negative;
  - `0x32`: `+0x374` (byte) non-zero and below `0x1A`.
- Placement starts at x `0x14`, y `0x534`. When `FUN_0044D870(...+0xDA8)` is not 1, visible widgets pack along x by each one's `+0x1C`; otherwise each next one steps y by `-0x80` (first y `0x4B4`). Hidden widgets take no slot.
- `this+0x10C2` is set to 1 when any widget is shown, else left 0.

The coordinates (y `0x534` = 1332) are larger than any 1999 screen, so they are in a virtual layout space, not device pixels; what space is unread. What each widget depicts, and what the player virtuals answer, is unread, so the name is LIKELY. `player-object.md` and `trigger-state.md` cite this routine as "the HUD" for its reads of player state.
