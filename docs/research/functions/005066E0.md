The queue is a 128-entry ring of 16-byte orders: a cost word (door def +0x95 or trap def +0x94), the kind byte at +2, the type id at +3, then three dwords, the first two the blueprint's point x and y (fixed point; Level 4 capture at 2340: (23,40), (25,40), (9,52)... matching the blueprints). Head +0x801, tail +0x802, count +0x803, an initialised byte +0x800 and the definitions pointer +0x804. The write goes to the tail slot and the tail wraps at 128, so an order written at tail 0 sets the slot-0 cost word that 0x00506B50 pays against. Reset 0x00506690 (from Player_Initialise), pop 0x00506970 (from Manufacture_AddPoints), removal by kind and type 0x005069E0 (from Door_Sell 0x004C3670 and Trap_Sell 0x004C3A20). The count (door arm 0x00506825..0x00506890, trap arm 0x00506754..0x005067CA): blueprints are things in the player's door list (+0xE; +0x109 nonzero) or trap list (+0xC; +0x10C bit 0x20) whose type +0xF6 equals the type argument; crates are things in the player's object list (+0xA) whose def +0xF4 has 0x10, +0x14A is the kind (0 door, 1 trap) and +0x14E is the definition's crate id (door def +0xB1, trap def +0xBC). It pushes only when blueprints outnumber crates; besides the cap it reads nothing of the ring. Call sites of this function: 0x004C356F (in 0x004C33B0), 0x004C3969 (in 0x004C3860), 0x0052116D (in 0x00520F40) and 0x00520F1A (outside a defined function). The count byte is the player +0xA1C that the Workshop finder 0x004F6200 tests; Job_Manufacture and states 63/69 test it too (their records). The ring layout is also in state-category-hooks.md section 3.4. Ours: ManufactureRules.TryQueue (crates only since ADR-0571; it had counted queued orders as crates), ManufactureRules.Enqueue (tail and slot-0 cost, ADR-0557) and PlayerState.ManufactureQueue (ADR-0231).
