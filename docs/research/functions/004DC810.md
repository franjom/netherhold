It walks the definition's list of byte[def+0x788] three-byte entries from def+0x5DA (a word whose low byte is the room or parameter and high byte the amount, then a kind byte; fetched by 0x00494380) and returns 1 only when all pass. The loader 0x0049355E-0x004935CA keeps a slot when 0x00569C40 returns non-zero, takes the kind from 0x00569C60 (file +0xDAC, our Present) and packs the low bytes of the two words from 0x00569C80 (RoomId low, RoomSize high). The kind goes through the five-entry jump table at 0x004DC8D4: kind 0 goes to 0x004DC8A6 and tests nothing; kind 1 (0x004DC858) calls 0x004C6EB0, which sums room+0xA7 (slab count) over every room of that type, and fails only when the sum is below the amount (JC at 0x004DC86B), so several small rooms add up and a size of 0 passes with none of the room owned; kind 2 (0x004DC86F) fails when player+0x7E (gold) is below the whole word, unsigned (JC); kind 3 (0x004DC87D) when player+0x82 (mana) is below it, signed (JL); kind 4 (0x004DC88E) calls 0x004BA7D0 with the zero-extended word and then compares its result with that word shifted right 16, which is 0, by JC, so it never fails. portals.md section 3 marks both-slots CONFIRMED and refutes the one-room reading. It is one of the gates the portal's candidate builder 0x004DBF90 applies per type (binary-entrance.md section 4.1); a type then also needs a non-zero weight there, which a Lair gives flat. Built as PortalRules.IsAttracted with all five kinds; only kind 1 ships.
