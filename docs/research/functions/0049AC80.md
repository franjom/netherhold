Whole decompile with scoped assembly windows read. Calls0x0048DEA0 and0x004BE090 in conversion branches. The full semantic classification and conversion behavior remain unsettled. Arm 0x14 (action 20) is built (ADR-0495) and so is arm 0x0049AF3D (action 33, ADR-0739); the rest is not attributed.

Arm 0x14 (action 20, read 2026-10-16): Object_Create_LIKELY(0x1C, owner +0x28, position +0x1A); on success Creature_PickUpCarriedThing 0x0048B350 with the new thing (refused when +0x3C3 is nonzero) and +0x92 |= 4 either way; on failure (0x0049AD92 JZ 0x0049B138) nothing is set. Both paths return 1.

It is the creature-level trigger action dispatcher (trigger-walkers.md: base 15, range 0x1C; its default calls the player dispatcher 0x004C8620). The possession calls above are inside its action arms. Case 0x23 (action 35, read 2026-10-04, Q227) reads byte 00:
- 0 clears `+0x3E6` bit 0x20 (no corpse) and sets 0x40 (no gold spill), then slot `+0x20` (`0x004B2AD0`) zeroes health so the entity pass removes the creature that turn.
- 1 calls `Creature_EnterDeathFall` `0x00459560`.
- Anything else does nothing and returns 1.

Arm 35's byte 0 is built (ADR-0744, trigger-action-arms.md): `TriggerExecutor` sets `CorpseSuppressed`, `DeathUncounted` and health 0, and `CreatureRemovalSystem` removes the creature. Byte 1 is unperformed (no shipped record).

Dispatch tables and three more arms (read 2026-11-11, OpenKeeper PR audit 1000-1110; STRONGLY INFERRED). The type is `[record+0xE] - 15`; above 0x1C it takes the default 0x0049B151, which passes ECX = `[creature+0x2A]` (the creature's owner) and the record to the player dispatcher 0x004C8620. Otherwise the byte table 0x0049B19C picks a slot of the jump table 0x0049B170: type 15 slot 0, 30 slot 4 (0x0049AF08), 33 slot 5 (0x0049AF3D), 35 slot 6 (0x0049AF68), 36 slot 7 (0x0049AFD0), 42 slot 8 (0x0049AFFA), 43 slot 9 (0x0049B0DE), every other index 10 the default.
- Type 33 (action 33, ALTER_SPEED): `Creature_SetSpeedMode` 0x004887D0 as (creature, byte0 != 0, 0) at 0x0049AF4A, so byte 0 of 0 walks and non-zero runs; returns 1. 72 shipped records (Level4, Level9, Level19, TrapTime). Built in `TriggerExecutor` (ADR-0739): `CreatureState.Running` takes byte 0 != 0, with no turn mark; why in [speed-set-turn.md](../speed-set-turn.md) "Deviations".
- Type 36 (action 36): `Creature_SetFlag46FBit0` 0x0048DF10 as (creature, byte0 == 1) at 0x0049AFDC: only operand 1 sets +0x46F bit 0, anything else clears it; returns 1. No shipped records.
- Type 43 (action 43): the arm at 0x0049B0DE packs `(+0x1A >> 12 & 0xFFFF) | (+0x1E >> 12 & 0xFFFF) << 16` (the creature's tile), leaves the record's +4 and +8 zero, sets id 4 and puts the creature's tag `[ESI+4]` in the word at record +0x10 (0x0049B0E4, 0x0049B11B). ECX is `[0x006E5050]` (the same world as 0x006E5054, Q231) and the call to `World_DispatchAction` 0x0050E5C0 is direct (0x0049B133); the arm returns 1. The bridge's id-4 handler 0x00442650 glides the camera to the tile centre and ignores the tag. There is no local-player test, unlike arm 26 of the player dispatcher (0x004C8753), whose test is at 0x004C86DB..0x004C86E4 and whose word holds the tree's player id. So any creature's tree moves the viewer's camera. STRONGLY INFERRED (read in DKII.EXE, not observed in play). Built in `TriggerExecutor` (ADR-0768) as a camera move to every viewer; the yaw words (zero here) are not modelled. Seven shipped records (Level1 x2, Level2 x2, Level3, Level15a, Level15b).
